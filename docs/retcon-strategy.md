# A source-grounded plan to beat Retcon

Tracker: [#16](https://github.com/stephanelee/robocode/issues/16). This is a prospective plan, not a performance result or permission to change several behaviors together. The scan-lag repair and tactical firing gates below were agreed prospectively with the independent reviewer before implementation outcomes; each candidate still requires its own immutable registration and review before measurement.

## Starting point and objective

The accepted AISurvivor source is [`b8d63ef49c1679db1893fd722c1306adfe9022be`](https://github.com/stephanelee/robocode/tree/b8d63ef49c1679db1893fd722c1306adfe9022be), with runnable JAR SHA256 `0d120a0461a7bf32b1c6d6277da34f9480309f255caa44e168e6bcdf8636bff2`. The opponent remains the unchanged official Java Retcon **0.2.0**, source [`28981c7a469ac064194b41001cd7183ec5ecf189`](https://github.com/robocode-dev/rumble-bots/tree/28981c7a469ac064194b41001cd7183ec5ecf189/bots/java/Retcon), with its own API 1.3.1 and the pinned Tank Royale 1.4.0 runner/server. Build AISurvivor with Java 17; run Retcon's source launcher with JDK 25. Exact opponent/dependency hashes remain in [the lock](../tools/opponents/retcon.lock.json).

The goal is an AISurvivor version that wins the repeated Retcon 1v1 matchup, rather than merely reducing one diagnostic. A proposed final confirmation is a frozen source/model tested in fresh, longer games: more than 50% AISurvivor score share, a majority of round wins, and a majority of game blocks won. For example, ten fresh 20-round games split across two independent batches would provide 200 confirmation rounds. The exact budget, aggregation, uncertainty method, and pass rules must be registered before that confirmation, not selected after seeing it. Report game-level variation and round-win intervals with their dependence limitations. This would establish opponent-specific performance, not general Robocode superiority.

The [three previous experiments](improvements.md) remain rejected under their original rules. They recorded useful observations, including fewer wall collisions, but no candidate met every registered criterion. This plan does not reinterpret those results or quietly reinstate their gameplay. Revisit an idea only with a new mechanism, evidence, and prospective experiment.

### Learning and persistence boundaries

Retcon constructs its real pipeline [once per game](https://github.com/robocode-dev/rumble-bots/blob/28981c7a469ac064194b41001cd7183ec5ecf189/bots/java/Retcon/src/fnl/bots/framework/adapter/tankroyale/TankRoyaleBot.java#L87). Its gun totals and surf danger persist across rounds in that process. [VirtualBullets.onRoundStart](https://github.com/robocode-dev/rumble-bots/blob/28981c7a469ac064194b41001cd7183ec5ecf189/bots/java/Retcon/src/fnl/bots/framework/targeting/VirtualBullets.java#L70) clears in-flight virtual shots, not the lifetime gun counts; enemy observations and active waves are reset. The inspected source has no learned model loaded across launches. Optional statistics are output, not a model import. Fresh processes therefore reset opponent adaptation; rounds within one game do not. Benchmark both early and later rounds rather than treating them as independent fresh opponents.

The gun selector has no recency weighting or contextual segments, so a changed AIS movement pattern may take time to change its preferred gun. Surf danger is likewise game-wide. Whether these limitations can be profitably exploited is unmeasured.

A lower-priority state-reset edge case deserves a diagnostic: [OrbitMovement's absolute last-reversal turn](https://github.com/robocode-dev/rumble-bots/blob/28981c7a469ac064194b41001cd7183ec5ecf189/bots/java/Retcon/src/fnl/bots/retcon/movement/OrbitMovement.java#L98) is not reset by [MovementStage](https://github.com/robocode-dev/rumble-bots/blob/28981c7a469ac064194b41001cd7183ec5ecf189/bots/java/Retcon/src/fnl/bots/framework/stages/MovementStage.java#L19). A reversal at turn 500 makes `now - lastReversalTurn < 10` true at the start of the next round. That can suppress fallback reversals until turn 510, but the primary surfer can still change direction. The incidence and competitive effect are unknown; this is not the basis of the first counter.

## Ordered implementation and experiment roadmap

Each behavior below needs a separate implementation PR, tests, immutable preregistration, matched-version comparison, recorded decision, and independent review. Do not combine several fixes to obtain an unattributable score change.

### 0. Observe the existing opponent before another behavior change

Under [observability issue #17](https://github.com/stephanelee/robocode/issues/17), enable Retcon's existing [StatsWriter](https://github.com/robocode-dev/rumble-bots/blob/28981c7a469ac064194b41001cd7183ec5ecf189/bots/java/Retcon/src/fnl/bots/framework/stats/StatsWriter.java#L25) with `RETCON_STATS_DIR` under the runtime JVM's actual `java.io.tmpdir`. A normal workspace output folder can silently disable these statistics. Preserve its per-game JSON before cleanup, source/runtime hashes, expected game/round identity, and missing-file status. Do not modify opponent source or use its internal statistics as an in-game policy input.

The existing output includes actual shots/hits, cumulative virtual-gun counts, detected/unanchored waves, hit-wave residuals, movement-prediction mismatches, and skipped turns. It does not expose the surf histogram or every branch decision. These exports are **offline diagnostics only**. During a match, AIS may use only its legal Bot API observations and its own history; it must never read Retcon's private files, observer truth, or internal current gun choice. A source-informed countermodel is legitimate only when uncertain enemy state is estimated from those observations. Label inferred states as estimates and retain unfavorable games too.

### 1. Correct AIS observation mechanics, one candidate at a time

**Bullet-energy scan lag, [issue #18](https://github.com/stephanelee/robocode/issues/18).** Tank Royale [scans before applying bullet hits](https://github.com/robocode-dev/tank-royale/blob/v1.4.0/server/src/main/kotlin/dev/robocode/tankroyale/server/core/TurnProcessor.kt#L75). Retcon carries those damage/bonus corrections forward, while accepted [AIS EnemyFireTracker](https://github.com/stephanelee/robocode/blob/b8d63ef49c1679db1893fd722c1306adfe9022be/src/main/java/EnemyFireTracker.java#L21) consumes corrections through the current scan turn. Test this exact fixture: prior scan 100, current scan 100, a later same-turn hit for 2 damage, next scan 98. It must infer no enemy shot on either turn. Add simultaneous genuine-fire, hit-bonus, scan-gap, and event-callback-order tests. The sole repair moves bullet damage and hit-bonus visibility from event turn `k` to scan turn `k+1`; wall and ram timing stays at `k`. Do not fold new gun-heat heuristics or a blanket shift of all events into this fix. Instrument inferred shots and uncertain scans; reduced false inference is a mechanism result, not automatically a strength gain.

**Radar/body decoupling, separately.** Accepted [AIS run setup](https://github.com/stephanelee/robocode/blob/b8d63ef49c1679db1893fd722c1306adfe9022be/src/main/java/AISurvivor.java#L131) sets gun/body and radar/gun adjustment but omits radar/body adjustment. The pinned server's [rotation rules](https://github.com/robocode-dev/tank-royale/blob/v1.4.0/server/src/main/kotlin/dev/robocode/tankroyale/server/core/TurnProcessor.kt#L422) add body rotation back in this combination. Verify the exact function when implementing: a body turn of +10 degrees and requested radar turn of -8 gives +2 without the third flag, versus -8 with it. Test both signs and zero turn. Measure fresh-scan fraction, scan-age histogram, longest gap, and reacquisition time. This fixes AIS observation; it is not an attempt to blind Retcon's strong radar.

### 2. Stop firing shots that miss the predicted target's angular footprint

The pinned engine [fires before applying intents](https://github.com/robocode-dev/tank-royale/blob/v1.4.0/server/src/main/kotlin/dev/robocode/tankroyale/server/core/TurnProcessor.kt#L65), so a same-turn gun rotation cannot repair a shot. [Java's radar/gun adjustment setter](https://github.com/robocode-dev/tank-royale/blob/v1.4.0/bot-api/java/src/main/java/dev/robocode/tankroyale/botapi/BaseBot.java#L608) also disables fire assistance; AIS already calls it. Its [fixed ten-degree gate](https://github.com/stephanelee/robocode/blob/b8d63ef49c1679db1893fd722c1306adfe9022be/src/main/java/AISurvivor.java#L400) is therefore a real alignment tolerance.

Candidate: cap that tolerance by a conservative angular half-width from the predicted interception range, retaining the existing ten-degree cap at close range. A proposed formula is `min(10 degrees, atan2(18, predictedRange))`, converted consistently to degrees. It is a footprint test, not a guarantee that the motion prediction is correct.

Deterministic fixtures: at range 500, a nine-degree ray misses the predicted centre by 78.217 units, while the collision radius is 18; a two-degree ray misses by 17.450. At range 100, nine degrees misses by only 15.643 and should remain allowed. Test angle wrapping, exact boundaries, stationary/moving predicted points, finite ranges, and use of the pre-turn heading. Instrument actual firing angle error, range, power, requests delayed by the gate, and hit/miss outcomes. Score and shot volume matter alongside hit rate: refusing almost every shot is not a successful gun.

### 3. Improve interception and endgame exposure as separate hypotheses

**Boundary prediction.** AIS [projects freely and clamps the final point](https://github.com/stephanelee/robocode/blob/b8d63ef49c1679db1893fd722c1306adfe9022be/src/main/java/AISurvivor.java#L384). The engine stops a bot at its first wall contact. In a constant-heading fixture with shooter `(400,300)`, target `(770,300)` heading 45 degrees at speed 8, an `800x600` arena and bullet speed 17, current prediction aims near `(782,499.288)`; the target's wall-contact point is `(782,312)`. Test physical stepping and first contact without assuming the enemy will continue sliding along a wall. Before a candidate, measure how often Retcon's observed path actually encounters this condition. Keep prediction changes separate from the firing gate and from previously rejected wall-smoothing changes.

**Energy exposure and finishing shots.** AIS [stops requesting fire below 12 energy](https://github.com/stephanelee/robocode/blob/b8d63ef49c1679db1893fd722c1306adfe9022be/src/main/java/AISurvivor.java#L774), whereas Retcon reduces power and caps finishing damage. Measure turns spent below that cutoff, remaining opponent energy, and outstanding bullets before choosing a reserve/low-power rule. Test engine minimum power, strictly sufficient own energy, retained movement reserve, and avoiding overpowered finishing shots. Change one rule per candidate. More low-quality shots can reduce survival; a lower cutoff alone is not a promised improvement.

### 4. Use coherent nonlinear 1v1 movement against its two guns

Retcon cannot select a circular, pattern-matching, or learned targeting gun in this pinned version. After correcting wave inference, a new movement hypothesis can use feasible curvature or change lateral velocity after an inferred enemy shot, with engine-correct acceleration and safe range/wall constraints. The aim is to invalidate both the head-on position and constant-velocity future position. Per-turn strategy resampling is not itself a coherent evasive trajectory; this is a control hypothesis, not evidence that the current learned policy's actual choices are uniformly random.

Start with deterministic kinematic tests for head-on and linear bullets at several distances. Include delayed shot detection, braking through zero, both lateral directions, close-range reversals that cross the head-on ray, and wall constraints. A far-range reversal fixture can evade both models; a close-range reversal can make head-on aim more dangerous. Choose timing/range rules prospectively from these mechanics, not from repeatedly tuning on score outcomes. Instrument reversals relative to detected shots, incoming-hit rate, wall exposure, and Retcon's two virtual-gun rates.

This is a shot-reactive movement controller hypothesis, not a reintroduction of the rejected general back-as-front steering change. Evaluate a coherent fixed duel policy first. If testing action persistence, credit the action actually executed and define how rewards, observations and elapsed decision time enter the learning update; do not merely ignore newly sampled actions while training them as if executed. Keep DQN and default online-training behavior as separately declared compatibility/safety evaluations; do not attribute a movement benefit to learning without testing that claim.

### 5. Only then test anti-surfer targeting

With reliable scans, firing, and movement established, predict Retcon's two physical orbit paths around the relevant wave origin. Test predicted positions against observed scans by range, time-to-wave-arrival, direction changes, and wall proximity. Compare a bounded-path aim with the accepted gun in its own experiment. Unknown danger history means the path choice is uncertain; do not pretend to know Retcon's private histogram.

Two later possibilities follow from its limited search: conditioning targeting on movement phase instead of one global history, or creating near-coincident wave arrivals that its one-wave decision does not jointly evaluate. An illustrative calculation assumes constant range 450 and cooling 0.1: a power-3 wave arrives after about 40.91 turns and a power-0.1 shot fired 17 turns later after about 39.84 turns. The [engine formulas](https://github.com/robocode-dev/tank-royale/blob/v1.4.0/server/src/main/kotlin/dev/robocode/tankroyale/server/rules/math.kt#L105) give speed `20 - 3p` and heat `1 + p/5`; [cooling and firing occur on separate branches](https://github.com/robocode-dev/tank-royale/blob/v1.4.0/server/src/main/kotlin/dev/robocode/tankroyale/server/core/GunEngine.kt#L34). Ordinary firing already creates several waves. Close arrival times alone are not a demonstrated hit pattern: moving origins, discrete timing, aim directions, bullet collisions, energy cost, and Retcon's actual responses all need deterministic tests and a separate preregistered trial. Do not start by training an elaborate gun on an unverified predicted trajectory.

## Measurement and review gates

The independent reviewer agreed the following categories prospectively. They do not replace or relax the three historical experiments' rules.

First collect a bounded diagnostic baseline with the unchanged accepted bot and optional Retcon statistics. Preserve all games, including missing telemetry and failures. Exploratory diagnostics cannot retroactively become a promotion test.

### Narrow engine-contract repair: bullet scan visibility only

This category is approved only for issue #18's bullet-damage/hit-bonus visibility repair from `k` to `k+1`, leaving wall/ram timing unchanged. Deterministic tests and the pinned engine's trace must establish that exact contract. Other radar, targeting, movement, or economy changes do not automatically inherit this category.

Primary: **120 fixed minimum-risk rounds**, three blocks of 20 rounds per version, with seeds **20261102, 20261103, 20261104**. Fixed mode does not use bot RNG, so these labels identify independent game replicates, not matched starts. Alternate arm order. All non-regression guards must pass:

- Equal-weight mean score-share change is **at least zero**.
- At least **two of three** block changes are **nonnegative**.
- No block loses more than **5 percentage points**.
- Candidate total round wins are no more than **three below** previous.
- Candidate records **zero skipped turns**.
- Candidate wall collisions per 1,000 turns are at most **1.2 times** previous; if previous has zero, candidate must also have zero.

After primary passes, retention still requires a **mandatory 120-round default online-training veto check**: the same three seeds, 20 rounds per version per seed, with a **fresh model and fresh seeded RNG for every version/seed game**. Both versions run their real default `train` mode; there are no frozen or imported checkpoints. Validate initially absent models, checkpoint-loaded status, per-round training counters, and the final counter of 20. Apply the same six guards above to this diagnostic. Any failed guard vetoes retention. This online-mode result is a product-mode safety check, not frozen-evaluation evidence. Its game scores are the veto's own objective, not an excluded pretraining phase. The complete successful sequence therefore uses 120 primary plus 120 online rounds; online scores never substitute for the fixed primary score.

The planned comparator interface, to be implemented and tested before use, is `--category correctness --policy fixed-minrisk` for the primary and `--category correctness --policy online-train` for the veto. `online-train` must map to actual runtime mode `train`; it is not an alias for frozen evaluation. Both invocations bind the same immutable registered plan, accepted previous source and candidate source, and the stated seeds/budgets.

Retaining this repair establishes correctness plus the declared non-regression checks. Label it **correctness retained, no strength gain established** unless a separately satisfied strength criterion supports more. A numerical score increase below five points is not the tactical improvement sought below.

### Tactical firing-cone candidate and later counters

Measured update: the narrower current-heading gate failed its separately approved48-round fast screen; [method and rejection](improvements/fire-alignment-screen.md) preserve the geometric rationale, actual score/efficiency regressions and exact gameplay restoration. The full confirmation gates below were not run or weakened. This counter has no accepted strength gain.

The firing-cone candidate keeps a **5-percentage-point minimum mean score-share gain** in a 120-round fixed minimum-risk primary, using the same three seeds and 20 rounds per arm. At least two blocks must **strictly improve**; the maximum block loss, win-loss allowance, zero-skips and wall-rate guards stay as above. Primary success must then pass the same mandatory 120-round fresh-model default online-training veto. The planned interface is `--category tactical --policy fixed-minrisk` for that primary and `--category correctness --policy online-train` for its non-regression veto. This is a separate tactical experiment, not part of the scan-lag repair.

Each later candidate needs its own reviewed registration, category, mechanism diagnostics, budgets and stopping rules before outcomes. No numerical guard is changed after a result is available. For the two designs above, complete the declared blocks unless evidence or process validity fails; invalid evidence stops the run and is not counted as a loss. Preserve and disclose a failed attempt before any corrected retry. Additional frozen-DQN diagnostics are optional only if declared prospectively; they cannot replace the mandatory default-online check.

Keep source, complete bundles, opponent, runtime, budgets, model initialization and configuration immutable within comparisons. Starts remain unpaired. Extend and test the comparison harness for default online mode before measurement; do not relabel an unsupported mode to fit it. Evaluate score guards from unrounded fractions and test inclusive zero/ratio boundaries.

After individual changes are retained, freeze the combined version and model for a fresh confirmation of the beating objective above. Do not reuse development games as confirmation or select only favorable seeds/rounds.

All implementation PRs require focused tests, a rebuilt tracked JAR with source parity, the standard build/sample/Retcon compatibility checks, durable raw evidence under `benchmarks/`, a report under `docs/`, and independent review/merge. Keep source-contract correctness, compatibility smoke, movement diagnostics, adaptation measurements, and a claim of beating Retcon distinct. Revert a rejected candidate's gameplay/JAR while preserving its plan and result. The interactive running game is outside this work.

No new candidate results are asserted by this document. The next concrete deliverable is reviewed observability and a locked experiment contract for the first isolated correction, under tracker #16.
