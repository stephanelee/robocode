## Verified API ordering and boundary

Pinned official Java Bot API1.4.0 `WebSocketHandler.handleRoundEnded` calls user RoundEnded before internal stopThread and final event-queue flush (lines177–190). Therefore blindly dropping all handlers immediately would lose legitimate queued terminal hit/win/death accounting. `handleRoundStarted` first runs internal stop/invalidate+queue clear/new thread waiting for first tick, then public RoundStarted (lines168–175); the replacement cannot observe a first tick before this callback finishes. These facts are verified against official v1.4.0 source and the exact cached API bytecode, not assumed from turn numbers.

Use a small two-phase lifecycle: RoundEnded marks CLOSING and stops further decision-loop/RNG/command mutations. Already queued terminal events remain accepted until the API's final drain. Before the next round reset (public RoundStarted), or final public GameEnded after the prior RoundEnded drain, seal the pending completed round: close gun/context/waves, flush queued wave observations exactly once, then serialize model and matching row under one adapter monitor. Next RoundStarted resets/reopens once. Duplicate end/seal callbacks are idempotent. Unknown unresolved gun cohorts stay pending/unknown; closing does not convert them to misses or modify learned results. Component mutators reject calls while closed, including query/prune/confirmed/removal and loop-related mutation. StartRound reopens and retains only existing intended persistent learning; danger decay remains once per new round.

All callback mutation and decision calculation use the same adapter monitor; `go()` and next-turn waits stay OUTSIDE it. Bot run threads carry an adapter round epoch so an old blocked run thread cannot mutate a reopened round. Ordered WebSocket dispatch and the verified API queue/thread invalidation remain the basis for epoch-less terminal dispatch; no fabricated stale-event detection is claimed for arbitrary externally injected callbacks after reopen.

Pending rows are written before new-round reset, and the final row at GameEnded. A future performance harness must wait for expected final model/metrics completion before killing the client; this repair does not silently assume a process-close grace interval, change any old runner/evidence or start games. Unexpected abort/disconnect without a completed RoundEnded cannot fabricate a completed row.
