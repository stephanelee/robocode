# Independent preliminary review: MeridianBranch draft

Reviewed the text-only `/private/tmp/meridian-branch-proposal.md` against the frozen Peak `PeakRisk.java` and `MeridianPeak.java`. No candidate, alternative-controller replay, fixture matrix or game was executed. This is design feedback before registration, not implementation or acquisition clearance.

The bounded two-leg design is coherent. The target order is shared by both signs, uses legal decision-time geometry and insertion identity, and does not use a later observed bullet. The strict clear at k followed by a flip at k+1 avoids switching during the target sweep. A later held-suffix encounter gives a concrete reason to consider continuation without adding another trajectory. Risk remains a maximum over the entire path for each ray before weighting and wave summation. The four-plan ranking represents an immediate-sign value estimate, not an actuator commitment to the hypothetical second leg. The proposed screen has nine fresh games/45 rounds, and confirmation adds nine fresh games/180 rounds only after all screen gates pass: maximum18 games/225 rounds. The known-negative Peak comparator is legitimate for this new distinct mechanism; absolute Diamond/transfer and confirmation gates prevent treating a relative gain as rehabilitation of Peak.

Resolve these points in the registered protocol before implementation:

1. **Specify the exact arithmetic order for actual branch scores.** Frozen Peak initializes the scalar score with initial-switch cost, accumulates each of50 wall terms chronologically, then adds each wave's weighted ray peaks in retained-wave/ray order. Preserve that literal order for H−/H+ and aliases. Define exactly where the one future-flip cost is added for real B paths; for example, after chronological wall accumulation and before wave-risk addition. Do not reconstruct H scores from separately summed components. Store diagnostic components independently, with explicit rounding-reconciliation tolerance that does not enter policy comparisons. This matters because exact numeric comparisons/ties are part of the policy.

2. **State the monotone-radius domain behind the i0 alive test.** Frozen Peak initially sets all ray flags true and first tests the near point at step1, whereas the new draft explicitly tests i0. With an inferred origin inside the arena, nonnegative near0 and positive speed, an i0-dead ray cannot re-enter, so the future numerical score should agree. Retain the literal frozen calculation for held-score parity, and use the additional i0 eligibility mask separately, or prove/enforce the legal-domain equivalence. Do not silently change held arithmetic, clamp a negative radius or introduce a new wave-retirement rule. Specify treatment of nonfinite/illegal wave inputs as invariant failure, with no policy fallback.

3. **Name the precise later-wave and target-death meanings.** Existing text says target ray survival, so a branch remains allowed when one target ray survives even if every other target ray died; it is suppressed only after the last target ray dies before/on k. Confirm this explicitly. Likewise a later qualifying wave needs any surviving ray and radial annulus overlap, not the same angular ray being near the bot at k and j. The current radial-only interpretation is coherent and intentionally permissive; preserve it without post-result angular refinements. IDs must distinguish equal-valued inferred waves: monotone per-round ordinal, never a value-based deduplication, and ordinals are assigned once on inference rather than during enumeration.

4. **Make the step and alias counters unambiguous.** The exact maximum is198 motion steps:100 held plus two suffixes of at most49. A looser <=200 invariant is fine, but say counters count actual `PeakMotion.step` calls, excluding the already-held prefix and no alias re-simulation. Specify that cache eligibility scans/geometry operations are counted separately, not hidden as extra trajectory calls. Alias command/score object values are copied verbatim with zero future-flip cost; no recomputation. Tie precedence in the draft matches frozen Peak's sign− preference when both held values tie.

5. **Finish the trace/readiness contract before code.** Identify one required initial trace/round/header record, planning/nonplanning record schema and terminal sealed trace manifest, including count/byte/hash/last sequence and explicit permanent write-failure state. Specify whether flush/end records count toward both caps; cap exhaustion must not require writing a failure record beyond that cap. Require final trace closure and state seal to be causally joined before endpoint readiness succeeds, including closing callbacks; a mere existing trace file or a marker plus sleep is insufficient. Distinguish buffer size from bounded record-construction memory: a128KiB output buffer alone does not bound an arbitrarily growing JSON builder. Bound each constructed record and live revision/reference storage without retaining the full game in memory. Define all timings as diagnostics only, with trace-writing separate from planner timing.

6. **Register failure-detection boundaries and evidence-upload limits honestly.** Private skips/trace failure can stop via the owned monitor; observer-only skips and completed recording/model checks have a game-boundary detection limit as in Peak. Do not promise immediate observation of a signal unavailable to the bot. Nine1680s process caps plus600s margin exactly consume262min, but a512MiB/game uncompressed trace cap can leave substantial hashing/validation/upload work. State that admission is an upper game-budget policy, not a completion guarantee; preserve partial evidence if a job cap interrupts. Prospectively choose how all valid trace output is compressed/streamed and uploaded without omissions, and verify zero-game upload path with synthetic bounded data rather than changing caps after a live resource failure.

Nonblocking simplifications and limits:

- Cache ray headings/sines/cosines and wall-death schedules once per immutable decision snapshot if useful, but retain frozen floating expressions/order for H paths. Ray near-point wall death is independent of the own path; four copies of that schedule are unnecessary. No fifth own trajectory is needed.
- The trace is the largest new engineering surface. A small lossless event/revision stream plus per-decision references and exact plan decomposition is preferable to duplicating the full learner/bank every tick. Keep only fields required to reconstruct legal inputs, joins and scores. This is provenance, not a deployed model feature.
- To check source fidelity, include ordinary contracts where both signs have distinct k, target dies on k, only some target rays die, later waves have equal priorities/distinct IDs, and no-wave/one-wave branch aliases preserve exact selected first command. These are contracts, not a performance sweep or evidence of strength.
- Fresh controls are unpaired engine/opponent starts despite common own seeds. Gate equal-game means and per-game ratios exactly as written. No significance, causal attribution or branch-use postselection claim follows from a screen PASS. Zero activated branches remains a descriptive limitation, not a reason to replace games.
- Keep the full50-tick wall cost. This proposal changes continuation action space and adds a future switch penalty; it does not isolate either factor, alter horizon, fix aim calibration or prove multi-wave loss causation.
- Frozen runtime and dependency family, Java17 source/JAR checks followed by Java25 execution, collect-once/read-only verification, permanent stage refs, first-invalid stop, result-only publication and separate review/merge requirements are consistent with AGENTS and prior repairs.

Disposition: suitable to turn into a distinct prospective registration after the six points above are clarified. No implementation or benchmark clearance is granted by this preliminary review. Registered protocol review and later exact source/JAR/tool/runtime review remain required.
