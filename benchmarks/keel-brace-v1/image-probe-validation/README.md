# Prospective zero-game image-metadata probe implementation

This implements only the separately preregistered diagnostic question: is the inherited image-metadata disagreement already present before tool setup, or do the same setup-java/setup-python versions used by the bootstrap change the observed records? One bounded Ubuntu26.04 x86_64 job, one attempt, two snapshots of the SAME collector bytes. It does not fix/admit an image, translate versions, change a game allowlist, approve a different worker or run a benchmark.

Root must publish the exact diagnostic registration/source head and obtain independent code/protocol PASS before adding ONE run-keel-brace-image-probe label with the exact-head KEEL-BRACE-IMAGE-PROBE-CLEARED body token. The workflow is branch-scoped, same-repository, run_attempt1, serial/cancel-false and <=10minutes. No checkout exists. The first step writes reviewed inline collector bytes to an owned fresh RUNNER_TEMP script, then executes `/usr/bin/python3` before tool setup. setup-java@v4 Temurin17.0.21+9 and setup-python@v5 Python3.13.17 are then attempted solely to reproduce the diagnostic setup context; no Java/JAR/Gradle/bot/server/Retcon command is run. The same script runs via `/usr/bin/python3` again into after-tools. Actual setup step outcomes are separate named metadata, not hidden if setup fails. Original partial metadata is uploaded with always() even on diagnostic errors; final job status reflects collection/setup outcomes, not image agreement or runtime acceptance.

`tools/keel_brace_image_probe.py` is the sole operational source. `make_workflow.py` embeds those exact LF UTF8 bytes into `.github/workflows/keel-brace-image-probe.yml` with a literal single-quoted heredoc. Tests prove inline-source identity and reject CRLF or GitHub expression interpolation in the collector. Both phase artifacts retain complete executed collector bytes/SHA for comparison to each other and the published head. The source is preserved again inside each phase; post-outcome custody must compare both copies and fetch original provider API/job/log/ZIP metadata.

Read scope is only `/imagegeneration/imagedata.json`, `/etc/environment`, `/etc/os-release`, `/usr/lib/os-release`, optional `/etc/lsb-release`, `/proc/sys/kernel/random/boot_id`, and `.setup_info` under a runner root derived from actual matching `/proc/PID/comm` and `/proc/PID/exe` evidence. No guessed /home paths, commands, credentials/config files, cmdline, broad process environment, binary reads or network. Matching process names must be exactly Runner.Worker or Runner.Listener; executable must resolve to the named apphost under bin before its parent is called a runner root. Multiple observed roots are kept separately, never majority-voted. Discovery failures/caps/nulls are explicit. Unrelated process names/arguments are not emitted. Only ImageOS/ImageVersion process env values and explicit run/head/workflow/setup-outcome metadata keys are retained.

Every metadata capture preserves exact raw bytes before parsing, requested/resolved path, lstat/opened/after stat fields (mode/owner/size/mtime/inode/device), own read timestamps, captured SHA and all attempted read/parse errors. Arbitrary resolved symlink targets are not read. Files are observed, not immutable attestation. JSON accepts the source-backed array/group/detail form, one unique Runner Image, UTF8(BOM explicitly recorded), case-insensitive group/detail key binding like the runner, but rejects duplicate/ambiguous aliases and fields/malformed shape. Raw detail/lines and exact values remain distinct. /etc/environment parsing is strict literal syntax; duplicate/malformed/expandable values are errors, not sourced/evaluated or replaced from process env. ENV, environment file, image file and each setup-info claim remain separate; there is no canonical version, mapping, comparison PASS or fallback.

Each source file capture is <=1MiB, with prefix/hash scope and diagnostics rather than a false whole-byte claim if oversized. Each phase payload is <=5MiB minus32KiB ZIP overhead reserve, with <=4MiB raw/parsed/code budget and reserved report/status headroom. The complete two-phase payload plus64KiB archive overhead reserve is <=10MiB. Oversize reports/parsed files are explicitly retained as prefixes and never acceptance. Discovery scans <=512 numeric PID entries and <=16 matching processes, collection deadline120seconds per phase, JSON group count<=128 and full parsed Runner Image detail<=65536characters (larger full detail remains in its original raw capture if complete). All limits are diagnostic-only, with missing/unscanned scope retained honestly.

Twenty-one pure tests use only fake temporary files/proc layouts, literal parser inputs and mocked capture sources; no subprocess/network/game/engine/tool setup is started. They cover matching-root discovery, refused guesses/symlinks, errors/caps, duplicates and malformed values, source separation, unset versus empty env, before/after budget, exact inline code and a complete mocked capture containing contradictory values that MUST remain contradictory even when collection succeeds. Earlier attempt1 failed4tests/1error because macOS fixture temp paths used /var aliases instead of canonical /private/var; actual log is preserved. Resolving fixture roots fixed that test assumption; production resolved-path allowlist was not widened. Attempt2's20tests and final21tests pass. These are implementation contracts only, not observed runner evidence.

The historical single-phase source in history/ was never used to collect a worker or run a job; it records the pre-outcome design refinement, not a discarded probe outcome. No gameplay candidate, existing harness, protocol game criterion, allowlist, old record, JAR, branch/ref/receipt or label was modified by this task.
