## Finding: ram correction epoch is a demonstrated narrow defect

Keel.java lines68/86–107 and unchanged KeelHelm.java lines72/90–111 put every legal energy correction into a single map keyed by event turn, then infer enemy fire at scan turn T using only map[T−1]. That lag is appropriate for bullet damage/bonus events but wrong for bot collisions.

Pinned official engine1.4.0 commit `c8ad3a8d19a843f6258d6f6f9db7f29229963903` explicitly fires, moves, handles wall/bot collisions, scans, advances bullets, then applies bullet collisions, in that order: [TurnProcessor.kt lines63–85](https://github.com/robocode-dev/tank-royale/blob/c8ad3a8d19a843f6258d6f6f9db7f29229963903/server/src/main/kotlin/dev/robocode/tankroyale/server/core/TurnProcessor.kt#L63). Thus the enemy scan at T already includes bot-collision damage from T; bullet damage/bonus applied after scan T appears in the next scan. Do not shift the whole correction map.

Both bots lose exactly RAM_DAMAGE=0.6 for each detected bot collision, independent of which one is classified as ramming: [CollisionDetector.kt lines330–368](https://github.com/robocode-dev/tank-royale/blob/c8ad3a8d19a843f6258d6f6f9db7f29229963903/server/src/main/kotlin/dev/robocode/tankroyale/server/core/CollisionDetector.kt#L330), [rules.kt line67](https://github.com/robocode-dev/tank-royale/blob/c8ad3a8d19a843f6258d6f6f9db7f29229963903/server/src/main/kotlin/dev/robocode/tankroyale/server/rules/rules.kt#L67). `isRammed` controls scoring attribution/which ramming bot stops; it does not condition the victim energy loss. The HitBot event carries victim post-collision energy, position and attribution: [HitBotEvent.java lines44–85](https://github.com/robocode-dev/tank-royale/blob/c8ad3a8d19a843f6258d6f6f9db7f29229963903/bot-api/java/src/main/java/dev/robocode/tankroyale/botapi/events/HitBotEvent.java#L44). Existing fixed −0.6 amount is correct for this pinned engine. MutableBot.applyDamage simply subtracts damage; no energy clamp changes that constant.

SDK default HitBot priority30 exceeds ScannedBot20, and same-turn events sort higher priority first: [DefaultEventPriority.java lines66–70](https://github.com/robocode-dev/tank-royale/blob/c8ad3a8d19a843f6258d6f6f9db7f29229963903/bot-api/java/src/main/java/dev/robocode/tankroyale/botapi/DefaultEventPriority.java#L66), [EventQueue.java lines174–187](https://github.com/robocode-dev/tank-royale/blob/c8ad3a8d19a843f6258d6f6f9db7f29229963903/bot-api/java/src/main/java/dev/robocode/tankroyale/botapi/internal/EventQueue.java#L174). Keel does not override these priorities. Therefore same-turn ram correction is available before its scan inference; this is operationally correctable without extra opponent inputs or delaying scans.

A source-derived example (not an executed fixture/result): enemy100→99.4 due solely to a collision at T. Current inference sees0.6 before using eventT's −0.6 at T+1, so it can add a phantom0.6 wave when other eligibility conditions hold. At T+1 a genuine0.6 shot can instead be canceled by that delayed correction. A simultaneous genuine shot of power p and ram at T should infer p, not p+0.6. With p near3 the current total can also fall outside the allowed power interval and suppress the true wave. These are accounting consequences, not claims about measured frequency or competitive cost.

Narrow candidate recommendation: route only HitBot's −0.6 to the inference epoch consumed by the SAME-TURN scan (for the current implementation, map[eventTurn−1], or a separately named same-turn correction bucket). Leave bullet-hit damage and hit-by-bullet bonus at their current eventTurn→next-scan epoch; leave wall heuristic, wave-origin/target timing, movement, all danger/learning constants, energy/power policy, gun and radar unchanged. Do not condition on isRammed or replace the amount with speculative variable damage. Prospective review should explicitly prove cleanup and missing-scan behavior before selecting an implementation.

## Gun chronology: do not claim an unverified defect

Keel aimAndFire lines129–149 launches from self[t] with fireTurn=t+1. Gun.Wave.radius(T)=(T−fireTurn+1)*speed, Gun.java lines18–23. Engine GunEngine fires before movement using pre-motion bot.position and gunDirection, emits BulletFired with the actual turn and bullet at its creation origin, then the turn advances the bullet once before collision checks: [GunEngine.kt lines48–104](https://github.com/robocode-dev/tank-royale/blob/c8ad3a8d19a843f6258d6f6f9db7f29229963903/server/src/main/kotlin/dev/robocode/tankroyale/server/core/GunEngine.kt#L48), [Bullet.kt lines24–55](https://github.com/robocode-dev/tank-royale/blob/c8ad3a8d19a843f6258d6f6f9db7f29229963903/server/src/main/kotlin/dev/robocode/tankroyale/server/model/Bullet.kt#L24). A request sent after snapshot t executes at t+1 from self[t], with one-speed radius against target scan position at t+1 for that turn's collision phase. Existing wave epoch/origin is consistent with that normal pipeline. Moving origin to self[t+1] or dropping the +1 would introduce a mismatch. No one-turn gun epoch defect was established.

`real=setFire(power)` is SDK acceptance, not confirmed firing. SDK checks current energy/heat and stores intent; the engine separately requires enabled/cold bot, delivered intent and energy strictly greater than requested power. [BaseBotInternals.java lines614–620](https://github.com/robocode-dev/tank-royale/blob/c8ad3a8d19a843f6258d6f6f9db7f29229963903/bot-api/java/src/main/java/dev/robocode/tankroyale/botapi/internal/BaseBotInternals.java#L614). SDK even accepts energy==power where engine rejects. That generic counterexample is excluded by Keel's stronger energy>power+0.1, heat==0 and other firing guards. Firing occurs before new movement/collision losses. Under normal delivered next-turn intent, no source-derived rejection path specific to Keel's guarded request was demonstrated. Network/deadline/termination differences are possible but must be measured, not invented.

onBulletFired currently registers only surfer own-bullet shadows, using previous-turn self origin. Gun.observe trains main on every fresh virtual wave and surf/selector only on accepted-request waves, using crossing proxies rather than actual bullet-hit labels. Gun class prose says “confirmed,” but implementation and existing baseline clarification explicitly disclose request semantics. Request/confirmation distinction is real documentation/semantics scope; it does not alone establish an active competitive defect or justify a new gun. A confirmation-matched learning implementation would need pending-request/event identity design, rejection/late-event handling and explicit prediction-cohort rules. Do not bundle that redesign into the ram repair or change successful power economics.
